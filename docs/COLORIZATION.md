# 漫画 AI 自动上色方案

[English](COLORIZATION.en.md) | 简体中文

调查日期:2026-11-04。本文件只安排复用上游项目的实现计划、能力边界、性能与验证方法;没有下载模型、运行推理、训练或处理用户漫画。所有性能数字在实际设备、固定模型、分辨率、批量和后端上测得前都属于未测量。

## 1. 直接复用的范围

| 层级 | 可直接引用 | 不自维护的内容 | 本项目边界 |
|---|---|---|---|
| 任务运行时 | [ComfyUI](https://github.com/Comfy-Org/ComfyUI),GPL-3.0 | 模型图执行、队列、缓存、模型加载 | 通过用户配置的本地/远端HTTP服务接入,不复制其Python运行时进App |
| 扩散模型框架 | [Diffusers](https://github.com/huggingface/diffusers),Apache-2.0 | 管线、调度器、设备/精度适配 | 作为服务端/研究环境依赖,不要求iOS内置Python |
| 线稿/参考条件 | [ControlNet](https://github.com/lllyasviel/ControlNet),Apache-2.0 | 条件网络实现 | 选具体模型和权重时再核许可证及硬件要求 |
| 参考图上色 | [MangaNinjia](https://github.com/ali-vilab/MangaNinjia) | 研究代码/权重 | 当前仓库LICENSE为CC BY-NC4.0,不能直接纳入通用/商业发行;仅在许可条件符合时作为可选外部服务/模型 |
| 专用漫画模型 | [manga-colorization-v2](https://github.com/qweasdd/manga-colorization-v2) | 生成器/去噪器权重 | 仓库元数据无SPDX,根目录也未找到LICENSE;权重来自外部下载。未确认许可前不打包、不分发 |
| 浏览器集成参考 | [BinitDOX/Manga-Colorizer](https://github.com/BinitDOX/Manga-Colorizer),MIT | 客户端调用外部上色服务的产品模式 | 可参考其“客户端+服务”边界;其依赖的v2模型仍受原许可约束 |

ComfyUI源码已确认存在按`prompt_id`/`job_id`取消的路径,包括`/api/jobs/{job_id}/cancel`和运行/排队任务处理。具体部署版本可能不同,适配器必须先探测能力。共享服务器禁止发送不带任务ID的全局`/interrupt`,以免取消别人的任务。

## 2. 能力与产品边界

- 首期输入:用户有权处理的单页/选定范围,保留原图;输出为派生缓存,不覆盖下载原件或源站文件。
- 两种模式:快速单页预览;整章后台队列。用户选择范围、风格/参考图和是否保留网点纹理。
- 角色一致性:优先使用参考图/调色板/已确认页面作为条件,不承诺模型自动记住整部作品的所有角色。跨页不一致时允许锁定颜色后重跑受影响页面。
- 文字与线稿:文字、气泡、声效应尽量保持原像素;首期没有可靠文字分割器时采用保守蒙版和用户可调保护强度,不宣称OCR已完美。
- 质量操作:接受、重试、恢复原图、只重跑选区;保存模型、工作流、参数、种子和源图哈希,保证同一结果可追踪。
- 安全与授权:只处理用户选择且有权修改的内容;不自动上传整库。外部服务需明确上传、保留、账号与删除策略。
- 离线:未配置且未安装本地推理服务时,功能显示不可用及原因,不影响阅读。

## 3. 插件形态

插件是JavaScript编排器,不是模型容器。它声明:

- `id/version/runtime/capabilities`:首期`colorize.page`、`jobs.list/cancel`、`health`。
- `provider`:comfyui-http,地址、可选令牌、API能力版本。
- `workflows`:工作流JSON、输入节点、种子、参考图和蒙版槽位;工作流可替换而App不更新。
- `resources`:模型/权重的来源、版本、许可证和最小显存/内存声明。资源由推理环境管理。
- `limits`:单页超时、最大边长、并发和缓存保留。

宿主负责图片字节解码/编码、任务持久化、进度、取消、账号/来源隔离和磁盘配额。插件不能直接访问用户全库、凭据库或任意服务器。建议的结果记录包含`sourceHash/workflowHash/modelHashes/seed/params/resultHash/createdAt`,缓存键变化即自然失效。

## 4. 性能安排

性能分三层记录,不互相冒充:

1. 上游公开数字:引用时保留硬件、分辨率、精度、批量和版本。本轮没有把任何GitHub README数字转写为产品指标。
2. 服务往返预算:提交、排队、首进度、完成、取消生效、结果下载分别计时;客户端UI在100ms内给出已排队/可取消状态属于交互目标,不是推理速度。
3. 推理实测:固定夹具页、模型、分辨率和种子,至少报告冷启动、热缓存单页、连续10页、峰值显存/内存、磁盘增量、取消后资源释放和失败恢复。Windows/macOS/远程GPU/iOS分别记录。一次测量不外推所有机型。

客户端内存可先按像素算底线:1024×1536的RGBA单缓冲为6MiB,1440×2160约11.87MiB,2048×20000长条约156.25MiB,均不含解码副本、模型或GPU工作区。默认每设备一个前台生成任务、仅预取邻近一页;长条采用受控切片并专门检查接缝/跨片配色。GPU峰值不能由这组输入缓冲数字推算。

首期目标是正确性和可控性,不预设“每页N秒”的承诺。实现后先在开发者机器记录基线,再决定是否需要批处理、低分辨率预览或端侧模型。端侧方案必须先证明包体积、电量、热量、内存峰值和取消行为可接受。

## 5. 实施顺序

1. 使用固定版本ComfyUI和已确认许可的测试工作流,在隔离服务完成健康检查、单页提交、进度、精确取消、失败和重启恢复。
2. 实现image-enhancer宿主与JS适配器,夹具图不进入用户库;验证原图哈希不变、缓存隔离、并发上限和重复请求合并。
3. 接入阅读器的单页动作:生成、对比、接受/撤销。此时仍不做整库自动处理。
4. 增加章节队列、暂停/恢复、磁盘配额和服务离线重试。
5. 评估参考图一致性、文字保护和工作流参数;每项以视觉夹具和用户可撤销为验收,不凭模型名称通过。
6. 只有服务方案稳定后,才评估可再分发的端侧模型。许可证未确认或非商业的模型保持外部可选,不进入默认安装包。

GPU、模型许可、云服务账号和费用属于外部条件。没有这些条件时,计划中的协议、任务生命周期、缓存和取消仍可先用模拟推理服务开发,但不能把模拟结果写成画质或速度验收。
