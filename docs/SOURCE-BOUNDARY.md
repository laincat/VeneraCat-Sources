# 源合集与多端统一边界

[English](SOURCE-BOUNDARY.en.md) | 简体中文

2026-11-04用户明确纠正:插件、扩展、订阅源等多端统一,不要拆开;支持端写在源条目中;简单功能可参考Surge模块,但都按源形成合集。本页取代初版“按三个项目生成目录”的设计。

## 1. 层次

| 名称 | 含义 | 不承担的职责 |
|---|---|---|
| 源/合集 | 一个发布者维护的稳定内容集合,有source.id、版本、说明与entries | 不是某个客户端专属仓库,不直接执行条目 |
| 条目 | 一个插件、扩展、主题、模块、服务或其他源引用 | 不因iOS/桌面分别复制身份与版本 |
| 内容制品 | 条目版本对应的文本/JSON/JS包/资源,有地址、大小、哈希 | 不是账号数据,不是订阅状态 |
| 订阅 | 用户跟踪源合集的更新关系,含来源URL、选定渠道/版本与更新策略 | 不等于自动安装或启用全部条目 |
| 运行能力 | 客户端/运行时实际提供的API,用于判断条目能否启用 | 不自动授予所有平台能力或其他账号权限 |

历史Core文档已经区分来源索引、包容器和运行能力,并保留Origin/IndexURL及正文哈希。这里继续保留这些边界,补上统一合集。既有ComicSource语境中的“漫画源”是具体内容提供插件,不要为了新的合集名词破坏其协议。

## 2. 同一合集供所有端使用

允许注册多个源,每个源各自维护一个跨端合集;本工程先提供官方合集。来源可以按发布者或内容定位划分,不按客户端划分。

唯一维护入口是`catalog/source.json`,构建只生成一份`build/source.json`。合集按内容kind分类,不是按客户端或操作系统拆目录。Core是共享运行时,不是要独立订阅第三份内容的消费端。

每条目包含:

- `id/kind/name/version/status`:身份、种类与成熟度。
- `supports.platforms`:如ios、macos、windows;iPadOS归入ios。
- `supports.requiresCapabilities`:如video-source.js、theme.legacy-json、service.v1。
- `artifact`:真正可取的内容及SHA/大小;计划条目没有artifact。
- `verification`:作者声明与实测范围分开,支持端不是验收证据。

```json
{
  "id": "service.tmdb",
  "kind": "service",
  "status": "experimental",
  "supports": {
    "platforms": ["ios", "macos", "windows"],
    "requiresCapabilities": ["service.v1"]
  }
}
```

内容身份为`source.id + entry.id`,同一内容只维护一个版本和制品。下载URL或镜像地址不是身份;不能仅因同名就让另一个来源接管已有安装。现有Registry仍按旧脚本key处理冲突,不代表跨源同名脚本已可同时运行;迁移要显式映射或提示冲突,不暗改脚本key。

客户端根据平台、能力和状态判断可用性,不支持时说明具体缺少的能力。合集内容仍统一。账号、启用状态及个性化设置属于用户配置,是否跨设备同步由配置同步策略决定。

## 3. 分类与引用

统一合集可收录漫画/视频插件、Magpie供应商、service、image-enhancer、主题、页面扩展和settings-module。插件的运行形式可以不同,但共享来源归属、版本与更新管理。

需要聚合其他来源时,用明确的source-reference条目声明另一个合集的身份/URL,保留原发布者。订阅外层合集不自动信任、递归启用或执行内层所有内容。当前原型未实现远程合集递归解析。

`build/compat/vcvideo.json`仅是同一合集的旧视频格式适配,由构建器生成,没有第二份内容权威或平台目录,待统一合集安装视频源打通后再退役。当前Core合同探针仍通过该旧视频适配验证安装;新的统一源消费者接入仍需客户端补齐。

## 4. Surge风格的简单模块

参考[Surge官方Module文档](https://manual.nssurge.com/profile/module.html):可读元信息头、INI分节、配置覆盖/撤销的思路。只参考这种轻量形式,不宣称原生导入任意.sgmodule,也不继承代理、MITM、网络脚本等语义。

本项目的草案扩展名为`.vcmodule`,样例位于`templates/modules/reader-preferences.vcmodule`。一个简单模块可以只声明阅读偏好或主题token覆盖,无需完整JS程序。模块也必须作为同一合集的条目,并声明所需能力。

首期设计只处理宿主明确列出的设置键,不支持脚本执行、任意文件、账号密钥或全局网络拦截。未来执行器优先使用成熟INI解析库,不自行维护通用解析器。未知节/键或缺失能力应明确拒绝,不能悄悄半生效。

覆盖层应保存为独立overlay:有效值由基础配置和有序启用的模块计算;停用模块移除其覆盖,不把用户原配置永久重写。当前仅落地格式样例和合集制品,没有客户端模块执行器。

## 5. 包与权限

合集统一不代表所有条目共用运行时或账号。JS插件、Magpie包、主题数据和简单模块继续按各自宿主执行;网络、凭据、文件与页面能力仍由平台桥按条目及账号范围提供。

保持两种摘要的含义:现有单文件源的SHA是正文哈希,压缩包新增整包哈希,不混填。摘要不证明发布者身份。订阅、安装、启用和授权是不同动作,一个合集不能因为已订阅就获取全库/全账号权限。

## 6. 本轮落地

已保持单一跨端合集结构,无按客户端拆分的发布目录。Trakt/TMDB/Bangumi 三个服务包已作为 `service.js` 压缩包进入 `catalog/packages/` 与统一构建产物（`fixture-verified`,离线夹具与真实 Core `service.Store`/`service.Runtime` 校验通过,不含真实账号验收）；`templates/modules/reader-preferences.vcmodule` 与合集 `settings-module` 条目保持元信息头与声明式配置节一致。

后续先实现统一源消费与条目能力匹配,再接客户端服务面板与声明式模块执行器。所有端共用相同源及条目身份,UI只表现兼容性和用户选择,不生成各自维护的源集合。
